# سامانه حضور و غیاب پرسنل

سامانه ثبت خودکار ورود و خروج پرسنل کارخانه با **تشخیص چهره**، همراه با پنل مدیریت
آنلاین، مدیریت شرح وظایف، و گزارش‌گیری روزانه/هفتگی/ماهانه با خروجی اکسل.

رابط کاربری **کاملاً فارسی و راست‌به‌چپ** است و همه تاریخ‌ها بر پایه **تقویم هجری شمسی**
و ساعت **تهران** محاسبه و نمایش داده می‌شوند.

---

## معماری

سامانه از دو بخش تشکیل شده که مستقل از هم اجرا می‌شوند:

| بخش | فناوری | نقش |
|---|---|---|
| `backend/` | Python + FastAPI + SQLAlchemy | API، پایگاه داده، محاسبه گزارش‌ها، خروجی اکسل |
| `frontend/` | React + TypeScript + Vite + Tailwind | پنل مدیریت **و** برنامه تبلت ورودی (یک برنامه، دو مسیر) |

دو صفحهٔ اصلی برنامه:

- `/` → **پنل مدیریت** (نیازمند ورود با نام کاربری و رمز)
- `/kiosk` → **تبلت ورودی کارخانه** (بدون ورود کاربر؛ با «کلید دستگاه» احراز هویت می‌شود)

### چرا تشخیص چهره داخل مرورگر انجام می‌شود؟

خواسته اصلی این بود که **تبلت در قطعی اینترنت هم کار کند**. اگر تطبیق چهره روی سرور
انجام می‌شد، با قطع شدن اینترنت کل سامانه از کار می‌افتاد.

بنابراین:

1. مدل‌های تشخیص چهره (حدود ۷ مگابایت) یک‌بار روی تبلت دانلود و توسط Service Worker
   کش می‌شوند.
2. تبلت «گالری چهره‌ها» (بردارهای عددی همه پرسنل) را می‌گیرد و در IndexedDB نگه می‌دارد.
3. تشخیص چهره کاملاً **محلی** انجام می‌شود — بدون هیچ ارتباطی با سرور.
4. تردد ثبت‌شده اگر اینترنت باشد فوراً ارسال می‌شود، وگرنه در صف محلی می‌ماند و
   به‌محض وصل شدن، به‌صورت دسته‌ای همگام‌سازی می‌شود.

هر تردد یک شناسه یکتا (`client_uuid`) دارد که روی تبلت ساخته می‌شود؛ به همین دلیل
ارسال دوباره یک بسته هرگز رکورد تکراری نمی‌سازد.

> **نکته مهم درباره بردارهای چهره:** بردارها عمداً نرمال‌سازی **نمی‌شوند**. آستانه
> استاندارد و آزموده‌شدهٔ این مدل (۰٫۶) روی بردار خام تعریف شده است. سرور و مرورگر
> باید دقیقاً در یک فضای برداری کار کنند؛ اگر یکی نرمال‌سازی کند و دیگری نه،
> فاصله‌ها بی‌معنا می‌شوند و تشخیص چهره **بی‌سروصدا** خراب می‌شود.

## راه‌اندازی

### پیش‌نیازها

- Python نسخه ۳٫۱۱ یا بالاتر
- Node.js نسخه ۲۰ یا بالاتر

### ۱) سرور (backend)

```bash
cd backend
py -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
cp .env.example .env          # و سپس SECRET_KEY را حتماً عوض کنید
./.venv/Scripts/python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

در اولین اجرا، جدول‌ها ساخته می‌شوند و این داده‌های پیش‌فرض ثبت می‌شود:

- کاربر مدیر: `admin` / `admin1234` — **بلافاصله رمز را عوض کنید**
- شش واحد سازمانی و چهار شیفت کاری نمونه
- تعطیلات رسمی با تاریخ ثابت شمسی (نوروز، ۱۳ فروردین، ۲۲ بهمن و…)

مستندات کامل API روی `http://localhost:8000/docs` در دسترس است.

### ۲) رابط کاربری (frontend)

```bash
cd frontend
npm install
npm run dev
```

پنل مدیریت: `http://localhost:5173`

### ۳) داده نمونه (اختیاری، فقط برای آزمایش)

```bash
cd backend
./.venv/Scripts/python.exe -m scripts.seed_demo
```

۱۲ پرسنل، ۴۵ روز تردد واقع‌نما (شامل تأخیر، اضافه‌کاری، غیبت و ورود بدون خروج)،
چند مرخصی و هشت وظیفه با سوابق انجام می‌سازد.

## راه‌اندازی تبلت ورودی

### گام اول: HTTPS (بدون آن دوربین کار نمی‌کند)

مرورگرها فقط در «بستر امن» به دوربین اجازه دسترسی می‌دهند: یعنی `localhost` یا
**HTTPS**. چون تبلت از طریق IP شبکه داخلی به سرور وصل می‌شود، **بدون HTTPS دوربین
اصلاً باز نمی‌شود** و تشخیص چهره کار نخواهد کرد.

سرور توسعه **همیشه روی HTTPS** بالا می‌آید. دو حالت پشتیبانی می‌شود:

**الف) گواهی خودکار (پیش‌فرض).** افزونه `@vitejs/plugin-basic-ssl` خودش یک گواهی
موقت می‌سازد؛ کاری لازم نیست. عیبش این است که روی تبلت هر بار باید هشدار مرورگر را
رد کنید (Advanced → Proceed).

**ب) گواهی ثابت و قابل‌اعتماد (پیشنهادی برای نصب دائمی).** اسکریپت `create-cert.ps1`
یک گواهی self-signed برای IP سرور می‌سازد:

```powershell
./create-cert.ps1
```

اگر `cert.pem` و `key.pem` در ریشه پروژه باشند، همان‌ها استفاده می‌شوند (و گواهی
خودکار غیرفعال می‌شود). سپس `certificate.pfx` را روی تبلت به‌عنوان گواهی معتبر نصب
کنید تا دیگر هیچ‌وقت صفحه هشدار نبینید.

> اگر IP سرور عوض شد، `$ip` را داخل `create-cert.ps1` به‌روز کنید و دوباره اجرایش کنید.

### گام دوم: ساخت دستگاه

در پنل مدیریت: **تنظیمات ← دستگاه‌ها ← ثبت دستگاه**.

کلید نمایش‌داده‌شده **فقط همان یک‌بار** دیده می‌شود؛ آن را کپی کنید.

### گام سوم: اتصال تبلت

روی تبلت به آدرس `https://<IP سرور>:5173/kiosk` بروید، کلید دستگاه را وارد کنید و
دکمه «اتصال به سرور» را بزنید. از این پس تبلت آن را ذخیره می‌کند و مستقیم بالا می‌آید.

پیشنهاد می‌شود صفحه را به‌عنوان اپلیکیشن روی صفحه اصلی تبلت نصب کنید
(Add to Home Screen) تا تمام‌صفحه و بدون نوار مرورگر اجرا شود.

تبلت هر دو دقیقه وضعیت خودش (تعداد ترددهای ارسال‌نشده و نسخه برنامه) را به سرور
گزارش می‌دهد؛ این اطلاعات در **تنظیمات ← دستگاه‌ها** دیده می‌شود، پس اگر تبلتی
چند روز آفلاین بماند متوجه می‌شوید.

اگر بیش از یک نفر مقابل دوربین باشند، تبلت ثبت نمی‌کند و پیام «لطفاً تنها مقابل
دوربین بایستید» نشان می‌دهد — تا تردد به نام فرد اشتباه ثبت نشود.

> آیکون‌های PWA با `python -m scripts.make_pwa_icons` ساخته می‌شوند (اگر خواستید
> طرح را عوض کنید، همان اسکریپت را ویرایش و دوباره اجرا کنید).

### گام چهارم: ثبت چهره پرسنل

**پرسنل ← دکمه ثبت چهره** کنار هر نفر. برای هر پرسنل حداقل **۳ نمونه** از زوایای
مختلف بگیرید؛ دقت تشخیص روی تبلت به‌طور محسوسی بالاتر می‌رود.

تصویر از دستگاه خارج نمی‌شود — فقط یک بردار ۱۲۸ عددی به سرور می‌رود. تصویر کوچک
چهره صرفاً برای نمایش در پروفایل ذخیره می‌شود.

> اگر دوربین کار نکند، پرسنل می‌تواند با **کد پرسنلی + رمز پشتیبان** تردد بزند.
> این راه همیشه در دسترس است.

**ثبت چهره مستقیم از روی تبلت.** لازم نیست همیشه به پنل مدیریت روی یک کامپیوتر
دیگر برگردید — روی صفحه اسکن تبلت، آیکون سپر (🛡) کنار تنظیمات دستگاه را بزنید،
با حساب مدیر یا سرپرست وارد شوید، پرسنل را از فهرست جستجو کنید و همان‌جا نمونه‌های
چهره را با دوربین همان تبلت ثبت کنید. برای امنیت دستگاه عمومی:

- اگر چند دقیقه در حالت مدیر بی‌کار بمانید، خودکار خارج می‌شوید.
- دکمه «پایان و بازگشت» هم بلافاصله از حساب مدیر خارج و به صفحه اسکن برمی‌گردد.
- دسترسی فقط برای نقش **مدیر ارشد** یا **سرپرست** است؛ کاربر ناظر اجازه ندارد.

### تشخیص زنده بودن (ضد جعل)

بدون این مرحله، گرفتن عکس چاپی یا عکس روی گوشیِ یک همکار جلوی دوربین کافی است تا
تردد به نام او ثبت شود.

پس از شناسایی چهره، تبلت از فرد می‌خواهد **سرش را کمی بچرخاند و برگرداند**. یک عکس
ثابت هرگز نمی‌تواند این کار را انجام دهد. اگر در همین فاصله پلک زدن هم دیده شود،
همان کافی است و کار سریع‌تر تمام می‌شود.

نکته‌های پیاده‌سازی:

- جهت چرخش عمداً مهم نیست. تصویر روی صفحه آینه‌ای است و گفتن «به راست بچرخید»
  هم برای کاربر گیج‌کننده است و هم برای کد خطاخیز.
- اگر صورت از کادر خارج شود، چالش باطل می‌شود؛ وگرنه یک نفر می‌توانست چالش را
  انجام دهد و بعد عکس فرد دیگری را جلوی دوربین بگیرد.
- نوار پیشرفت روی صفحه نشان می‌دهد چقدر چرخش تشخیص داده شده — همین نوار برای
  تنظیم آستانه هم کمک می‌کند.

تنظیم از راه `.env`:

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `REQUIRE_LIVENESS` | `true` | خاموش کردن کامل این مرحله |
| `LIVENESS_TURN_THRESHOLD` | `0.06` | کمتر = آسان‌گیرتر |
| `LIVENESS_TIMEOUT_SECONDS` | `12` | مهلت انجام چالش |

> اگر پرسنل شکایت کردند که تأیید نمی‌شود، آستانه را کم کنید (مثلاً `0.045`).
> این عدد روی سخت‌افزار و فاصله دوربین شما باید یک‌بار تنظیم شود.

## امکانات

### حضور و غیاب

- تشخیص خودکار «ورود» یا «خروج» بر اساس آخرین تردد ثبت‌شده
- محاسبه تأخیر، تعجیل، کارکرد، موظفی و اضافه‌کاری بر اساس شیفت هر نفر
- پشتیبانی از شیفت شب (عبور از نیمه‌شب) — یک شیفت در گزارش دو تکه نمی‌شود
- تأخیر و تعجیل مجاز (grace) قابل تنظیم برای هر شیفت
- ثبت دستی و اصلاح تردد توسط مدیر (با برچسب مشخص در گزارش)
- تعطیلات رسمی و تعطیلات هفتگی؛ کار در روز تعطیل کاملاً اضافه‌کاری حساب می‌شود

### وظایف و شرح وظایف

- وظیفه یک‌باره با تاریخ سررسید، یا شرح وظیفه تکرارشونده (روزانه/هفتگی/ماهانه)
- ثبت انجام روزانه برای وظایف تکرارشونده
- اولویت، درصد پیشرفت، زمان برآوردی و هشدار «از موعد گذشته»

### مرخصی

- مرخصی روزانه، ساعتی، استعلاجی، مأموریت و بدون حقوق
- گردش تأیید؛ تا وقتی مرخصی تأیید نشده، در گزارش‌ها **غیبت** محاسبه می‌شود
- مرخصی ساعتیِ تأییدشده موظفی همان روز را کم می‌کند و اگر ابتدای شیفت باشد
  تأخیر ثبت نمی‌شود (مثلاً مرخصی ۸ تا ۱۰ و ورود ساعت ۱۰ = بدون تأخیر)

### گزارش‌ها

- روزانه، هفتگی (شنبه تا جمعه)، ماهانه (ماه شمسی کامل) و بازه دلخواه
- فیلتر بر اساس واحد سازمانی و پرسنل
- خروجی اکسل راست‌به‌چپ با عنوان‌های فارسی، تاریخ شمسی، رنگ‌بندی وضعیت،
  فیلتر خودکار و ردیف جمع کل
- چهار نوع خروجی: خلاصه دوره‌ای، ریز روزانه، ریز ترددها، و وظایف

> گزارش هرگز روزهای **نیامده** را غیبت حساب نمی‌کند؛ گزارش ماهانهٔ ماه جاری تا
> امروز محاسبه می‌شود.

### حریم خصوصی داده‌ها

تصاویر چهره و عکس ترددها داده شخصی پرسنل‌اند و **عمومی نیستند**. مسیر `/static`
با یک کوکی HttpOnly محافظت می‌شود که هنگام ورود مدیر ست می‌شود؛ بدون آن پاسخ
۴۰۱ برمی‌گردد. این کوکی از توکن اصلی جداست و فقط اجازه دیدن تصویر می‌دهد.

> در تولید حتماً `SECURE_COOKIES=true` بگذارید تا کوکی فقط روی HTTPS ارسال شود.

### دسترسی‌ها

| نقش | دسترسی |
|---|---|
| مدیر ارشد | همه چیز، شامل مدیریت دستگاه‌ها و کاربران پنل |
| سرپرست | مدیریت پرسنل، ترددها، وظایف و مرخصی‌ها |
| ناظر | فقط مشاهده گزارش‌ها |

## استقرار محلی با Docker (بدون دامنه، بدون Let's Encrypt)

برای آزمایش کل سامانه (پایگاه داده + سرور + رابط کاربری) با همان Dockerهای
تولید، ولی روی سیستم خودتان.

پیش‌نیاز: Docker با Compose نسخه ۲ (`docker compose version`).

```bash
make local-setup   # ساخت .env.local + گواهی HTTPS محلی (بار اول)
make local-up      # ساخت ایمیج‌ها و بالا آوردن سامانه
```

پنل مدیریت و مستندات API روی `http://localhost:8080` در دسترس‌اند (پورت را
می‌توانید در `.env.local` با `LOCAL_PORT` عوض کنید). چون آدرس `localhost`
است، مرورگر آن را «بستر امن» می‌داند و دوربین همین‌جا بدون HTTPS هم کار می‌کند.

### گوشی به‌عنوان تبلت ورودی (وقتی سیستم خودتان دوربین ندارد)

`make local-setup` یک گواهی HTTPS خودامضا هم برای IP شبکه داخلی سیستم
می‌سازد (`cert.pem`/`key.pem`، با تشخیص خودکار IP). خروجی `make local-up`
آدرس دقیقش را چاپ می‌کند، چیزی شبیه:

```
Phone/tablet (same network): https://192.168.100.217:8443/kiosk
```

روی گوشی (در همان Wi-Fi) همین آدرس را باز کنید. بار اول مرورگر هشدار «گواهی
نامعتبر» می‌دهد — رد کنید (Advanced → Proceed). برای اینکه دیگر این هشدار را
نبینید، `cert.pem` را روی گوشی به‌عنوان گواهی معتبر نصب کنید.

اگر IP سیستم عوض شد یا تشخیص خودکار درست نبود:

```bash
make local-cert IP=192.168.1.23
```

| دستور | کار |
|---|---|
| `make local-up` | ساخت و بالا آوردن سامانه محلی |
| `make local-down` | خواباندن سامانه محلی |
| `make local-cert` | ساخت/تازه‌سازی گواهی HTTPS برای دسترسی گوشی/تبلت |
| `make local-logs` | لاگ زنده |
| `make local-status` | وضعیت سرویس‌ها |
| `make local-seed-demo` | ساخت داده نمونه |
| `make local-destroy` | حذف کامل شامل پایگاه داده — برگشت‌ناپذیر |

> این مسیر جدا از استقرار VPS است (فایل `docker-compose.local.yml` و
> `.env.local` مجزا)، پس با هم تداخلی ندارند و می‌توانید همزمان از هر دو
> استفاده کنید.
>
> `cert.pem`/`key.pem` همان فایل‌هایی هستند که `vite.config.ts` برای سرور
> توسعه بدون Docker (`npm run dev`) هم استفاده می‌کند — با یک بار ساختن گواهی،
> هر دو مسیر از همان گواهی معتبرشده روی گوشی بهره می‌برند.

## استقرار روی VPS با Docker

کل سامانه (پایگاه داده، سرور، رابط کاربری) با Docker بالا می‌آید. **SSL و
مسیریابی دامنه‌ها روی nginxِ خودِ سرور (نه داخل کانتینر) انجام می‌شود** — چون
این پروژه معمولاً کنار چند پروژه دیگر، هرکدام با دامنه/زیردامنه خودشان، روی
همین یک VPS اجرا می‌شود و فقط یک nginx می‌تواند پورت ۴۴۳ را در اختیار بگیرد.
جزئیات معماری در «چند پروژه روی یک VPS» پایین همین بخش.

### روش سریع: از صفر تا کامل با یک دستور

روی یک VPS اوبونتو/دبیان **کاملاً تازه** (حتی بدون Docker):

```bash
git clone <آدرس مخزن> attendance-system
cd attendance-system
make bootstrap
```

این دستور Docker Engine و افزونه Compose v2 را نصب می‌کند، دامنه و ایمیل
Let's Encrypt را می‌پرسد (یا از متغیرهای محیطی می‌خواند)، `.env` را می‌سازد،
سامانه را بالا می‌آورد و گواهی SSL را می‌گیرد — همه در یک اجرا.

برای اجرای کاملاً غیرتعاملی (مثلاً در اسکریپت):

```bash
DOMAIN=hozur.example.com LETSENCRYPT_EMAIL=admin@example.com make bootstrap
```

روی سرورهای ایران، برای دور زدن فیلترینگ/کندی هنگام نصب Docker و دریافت
ایمیج‌ها:

```bash
MIRRORS=1 DOMAIN=hozur.example.com LETSENCRYPT_EMAIL=admin@example.com make bootstrap
```

### پیش‌نیاز (روش دستی)

- یک سرور لینوکسی (اوبونتو/دبیان) با Docker
- **Docker Compose نسخه ۲** (یعنی `docker compose` با فاصله، نه `docker-compose`
  با خط تیره). نسخه قدیمیِ جداگانه این فایل را نمی‌تواند بخواند و از سال ۲۰۲۳
  دیگر پشتیبانی نمی‌شود.
- یک دامنه که رکورد `A` آن به IP سرور اشاره کند
- پورت‌های ۸۰ و ۴۴۳ روی سرور آزاد باشند (nginx سطح میزبان از آن‌ها استفاده
  می‌کند — `make ssl` خودش nginx/certbot را در صورت نبودن نصب می‌کند)

بررسی نسخه Compose:

```bash
docker compose version
```

اگر خطای `unknown command: docker compose` گرفتید، افزونه نسخه ۲ نصب نیست:

```bash
make install-compose
```

### مراحل (وقتی Docker از قبل نصب است)

```bash
git clone <آدرس مخزن> attendance-system
cd attendance-system

make setup            # ساخت .env با کلیدهای تصادفی امن
nano .env             # DOMAIN و LETSENCRYPT_EMAIL را پر کنید؛ اگر پروژه
                      # دیگری هم روی این سرور هست، APP_HTTP_PORT را هم
                      # به یک عدد یکتا (که پروژه دیگر استفاده نمی‌کند) عوض کنید
make deploy           # ساخت ایمیج‌ها و بالا آوردن سرویس‌ها (فقط روی 127.0.0.1)
make ssl              # پیکربندی nginx سطح میزبان + گرفتن گواهی از Let's Encrypt
```

تمام. پنل مدیریت روی `https://<دامنه شما>` و تبلت ورودی روی
`https://<دامنه شما>/kiosk` در دسترس است.

> `make setup` رمز اولیه مدیر را تولید و چاپ می‌کند. یادداشتش کنید.

### چند پروژه روی یک VPS

معماری استقرار این‌طور است:

```
اینترنت ──HTTPS(443)──▶ nginx سطح میزبان ──HTTP(127.0.0.1:APP_HTTP_PORT)──▶ کانتینر web
                              │                                                  │
                              │  (یک vhost به‌ازای هر دامنه،                       └──proxy_pass داخلی──▶ کانتینر backend
                              │   deploy/nginx/app.conf.template)
                              ▼
                   پروژه‌های دیگر همین سرور
                   (هرکدام دامنه و APP_HTTP_PORT خودشان)
```

- **کانتینر `web` این پروژه هیچ پورتی به‌جز `127.0.0.1:APP_HTTP_PORT` باز
  نمی‌کند** (نه ۸۰، نه ۴۴۳) — از بیرون سرور اصلاً در دسترس نیست.
- `make ssl` (یعنی `scripts/deploy-host-nginx.sh`) روی خودِ سرور nginx و
  certbot نصب می‌کند (اگر از قبل نباشند)، برای همین دامنه یک vhost با نام
  `/etc/nginx/sites-available/<دامنه>.conf` می‌سازد و گواهی Let's Encrypt
  می‌گیرد. فایل‌ها و نام‌های مختص همین پروژه (vhost با نام دامنه،
  `attendance-security-headers.conf`) عمداً طوری نام‌گذاری شده‌اند که به
  تنظیمات پروژه‌های دیگر این سرور دست نزنند.
- برای استقرار پروژه دوم (یا سوم…) روی همین سرور: همین مراحل را در پوشه‌ای
  جدا تکرار کنید، فقط `APP_HTTP_PORT` را به عددی که پروژه‌های قبلی استفاده
  نمی‌کنند تغییر دهید. `make ssl` هم برای هر پروژه جدا اجرا می‌شود و فقط
  vhost همان پروژه را می‌سازد/به‌روزرسانی می‌کند.

### دستورهای روزمره

`make` را بدون آرگومان بزنید تا فهرست کامل را ببینید. پرکاربردها:

| دستور | کار |
|---|---|
| `make deploy` | ساخت و بالا آوردن کل سامانه |
| `make ssl` | گرفتن گواهی SSL (بار اول) |
| `make logs` | دیدن لاگ زنده |
| `make status` | وضعیت سرویس‌ها |
| `make backup` | پشتیبان از پایگاه داده و تصاویر چهره |
| `make restore FILE=...` | بازگردانی پشتیبان |
| `make update` | دریافت آخرین کد و راه‌اندازی مجدد |
| `make ssl-check` | آزمایش تمدید گواهی |
| `make down` | خواباندن سرویس‌ها (داده‌ها می‌مانند) |

### تمدید خودکار گواهی

بسته `certbot` روی سرور (نصب‌شده توسط `make ssl`) خودش یک تایمر systemd
(`certbot.timer`) دارد که روزی دوبار تمدید را بررسی می‌کند — مشترک بین همه
پروژه‌های این سرور، نه مخصوص این پروژه. `make ssl` هنگام اولین اجرا یک
«renewal hook» هم نصب می‌کند که بعد از هر تمدید موفق، nginx را reload
می‌کند. کاری لازم نیست؛ برای اطمینان: `make ssl-check`.

### نکته درباره اولین اجرای SSL

vhost نهایی به فایل گواهی اشاره می‌کند ولی گواهی هنوز وجود ندارد؛ از طرف دیگر
certbot برای تأیید دامنه به یک nginxِ در حال اجرا روی پورت ۸۰ نیاز دارد.
`make ssl` این بن‌بست را با نوشتن یک vhost موقتِ فقط-HTTP، گرفتن گواهی، و
سپس جایگزینی آن با vhost نهایی (HTTP→HTTPS + پراکسی) حل می‌کند.

> برای آزمایش، `LETSENCRYPT_STAGING=true` بگذارید تا محدودیت تعداد درخواست
> Let's Encrypt را مصرف نکنید.
>
> اگر پورت ۸۰ از بیرون در دسترس نیست (فایروال/NAT ارائه‌دهنده): `make ssl-dns`
> به‌جای `make ssl` — گواهی را با روش DNS-01 (دستی) می‌گیرد، ولی خودکار تمدید
> نمی‌شود.

## تنظیمات دستی (بدون Docker)

پیش از بهره‌برداری حتماً:

1. `SECRET_KEY` را با یک رشته تصادفی بلند عوض کنید:
   ```bash
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```
2. رمز کاربر `admin` را تغییر دهید.
3. `CORS_ORIGINS` را به دامنه/IP واقعی محدود کنید (به‌جای `*`).
4. برای تعداد پرسنل زیاد، به PostgreSQL مهاجرت کنید:
   ```
   DATABASE_URL=postgresql+psycopg://attendance:PASSWORD@localhost:5432/attendance
   ```
5. از فایل پایگاه داده و پوشه `backend/app/static/` (تصاویر چهره) پشتیبان بگیرید.
6. تعطیلات مذهبی قمری هر سال جابه‌جا می‌شوند؛ از **تنظیمات ← تعطیلات رسمی**
   دستی اضافه‌شان کنید.

### ساخت نسخه تولید فرانت‌اند

```bash
cd frontend
npm run build
```

خروجی در `frontend/dist/` قرار می‌گیرد و با هر وب‌سروری (Nginx، Caddy…) قابل سرو است.
فقط توجه کنید که مسیرهای `/api` و `/static` باید به سرور FastAPI پروکسی شوند.
